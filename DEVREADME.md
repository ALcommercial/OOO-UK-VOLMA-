# ВОЛМА · Умная логистика — техническая документация (DEVREADME)

Документ для разработчиков и технических экспертов. В нём описаны архитектура MVP, модель данных, обучение модели прогноза загруженности дорог, построение маршрутов, диспетчеризация перевозок и способы расширения системы. Пользовательская инструкция находится в `README.md`.

## 1. Обзор

| Параметр | Значение |
|---|---|
| Тип приложения | Десктоп, однопользовательское, офлайн |
| Язык | Python 3.9+ |
| GUI | Tkinter / ttk (стандартная библиотека) |

## 4. Модель прогноза загруженности (`ai/traffic_model.py`)

### 4.1 Постановка задачи

Целевая переменная — **коэффициент загруженности** участка `c ≥ 1`. Он показывает, во сколько раз фактические условия движения хуже свободного потока: `c = 1` — дорога свободна, `c = 2` — сильные заторы. Модель предсказывает `c` по участку дороги, дню недели, часу, погоде и наличию события.

### 4.2 Тип модели

В MVP используется **не нейронная сеть, а гребневая регрессия (Ridge) на сконструированных признаках**. Решение принято осознанно:

- данных пока мало: тысячи наблюдений, а не миллионы;
- модель интерпретируема: каждый коэффициент показан на вкладке «Аналитика ИИ» как вклад фактора, и это удобно объяснять на защите;
- обучение занимает доли секунды и не требует сторонних библиотек и GPU;
- нелинейность (пики трафика, взаимодействие «город × час») задаётся признаками, поэтому линейная модель достигает R² ≈ 0.93 на тестовой выборке.

Переход на нейросетевую модель описан в разделе 8.

### 4.3 Признаки (17)

| № | Признак | Формула / смысл |
|---|---|---|
| 0 | Смещение | 1 |
| 1 | Доля городских участков | `urban` |
| 2 | Утренний пик × город | `urban · exp(−(h−8)²/4)` |
| 3 | Вечерний пик × город | `urban · exp(−(h−18)²/5)` |
| 4 | Утренний пик | `exp(−(h−8)²/4)` |
| 5 | Вечерний пик | `exp(−(h−18)²/5)` |
| 6 | Ночь | `1`, если `h < 5` или `h ≥ 23` |
| 7 | Выходной | `1`, если суббота/воскресенье |
| 8 | Выходной × город | `weekend · urban` |
| 9 | Пятница | `1`, если пятница |
| 10–13 | Погода (one-hot) | дождь, туман, снег, гололёд; «ясно» — базовая категория |
| 14 | Дорожное событие | 0/1 |
| 15 | Плохое покрытие | `1 − quality` |
| 16 | Федеральная трасса | 0/1 |

Пики трафика задаются гауссовыми «колоколами» по часу суток. Так модель получает плавную суточную кривую, а не ступенчатую разметку часов.

### 4.4 Обучение

1. Из `traffic_history` загружаются наблюдения и сопоставляются с параметрами дорог.
2. Данные перемешиваются с фиксированным зерном (`seed = 7`) и делятся на обучающую и тестовую части в пропорции **80 / 20**.
3. Собираются нормальные уравнения с L2-регуляризацией (смещение не штрафуется):

   ```
   (XᵀX + λI′) · w = Xᵀy,   λ = 0.5
   ```

4. Система 17×17 решается **методом Гаусса с частичным выбором ведущего элемента** (`solve()`).
5. На тестовой выборке считаются метрики **R²**, **MAE** и **MAPE**.
6. Коэффициенты и метрики сохраняются в `model_meta` в формате JSON. При следующем запуске модель загружается без переобучения.

Сложность — O(N·F²) на сборку матрицы и O(F³) на решение, где F = 17. На ~11 500 наблюдениях обучение занимает около 0.15 с.

### 4.5 Инференс

```python
predict(road, weekday, hour, weather, event=0) -> clamp(w · x, 1.0, 4.0)
```

`Network` кэширует прогнозы по ключу `(road_id, weekday, hour)`. Кэш сбрасывается при каждом `refresh()`.

### 4.6 Цикл дообучения

После закрытия рейса на вкладке «Рейсы» для каждого пройденного участка в `traffic_history` добавляются три наблюдения («телеметрия»), и модель сразу переобучается. В MVP телеметрия синтетическая: её даёт та же генерирующая функция, что и при инициализации. В промышленной версии сюда подключаются данные GPS/ГЛОНАСС-трекеров (см. раздел 8).

### 4.7 Синтетическая обучающая выборка

`seed.true_congestion()` — скрытая «истинная» функция загруженности: пики, выходные, погода, покрытие, события и гауссов шум (σ = 0.06). Для каждой из 44 дорог генерируется 260 наблюдений. Модель не знает эту функцию и восстанавливает её по данным. Это позволяет честно оценить, насколько хорошо она обучается.

## 5. Построение маршрутов (`ai/network.py`)

### 5.1 Граф

- **35 узлов**: 9 заводов, 4 месторождения, 22 РЦ/клиента в РФ и Казахстане.
- **44 ребра**: федеральные, региональные и местные дороги, включая 4 пограничных перехода (МАПП).
- Длина ребра — расстояние по большому кругу (формула гаверсинуса), умноженное на коэффициент извилистости дороги: 1.18 для федеральных, 1.25 для региональных, 1.35 для местных.

### 5.2 Стоимостная модель участка

Для ребра длиной `d`, с качеством покрытия `q`, погодой `wx` и прогнозом загруженности `c` на момент въезда:

**Скорость и время**

```
v = v_base(cat) · (0.62 + 0.38·q) · k_speed(wx) / (1 + 0.55·(c − 1))
t = d / v + t_event + t_border
```

`v_base`: 78 / 64 / 42 км/ч. `k_speed`: ясно 1.0, дождь 0.92, туман 0.86, снег 0.78, гололёд 0.68. `t_event = delay(kind) · severity`, где базовая задержка равна 2 ч для ремонта, 3 ч для ДТП, 2.5 ч для пробки и 2 ч для погодного события. `t_border` по умолчанию 3 ч.

**Топливо**

```
L = d/100 · fuel_l_100 · (0.72 + 0.28·load_ratio) · (1 + 0.32·(c−1)) · (1 + 0.18·(1−q)) · k_fuel(wx)
```

**Дорожные сборы**: `d · toll_rub_km` плюс «Платон» (`d · platon_rub_km`) для ТС грузоподъёмностью от 12 т на федеральных дорогах РФ.

**Время ТС и водителя**: `t · (driver_rate + vehicle_rate)`.

**Ожидаемые потери груза**

```
rate = loss_base · d/100 · (1 + road_sens · (1−q) · 2) · (1 + wx_sens · risk(wx)) · (1 + 0.25·(c−1)) [+ надбавка за событие]
loss_rub = min(rate, 0.25) · load_t · price_rub_t
```

Для каждого груза заданы свои чувствительности. Например, у ГКЛ высокая чувствительность к покрытию (3.0) и погоде (2.6), у цемента навалом — низкая (0.8 и 0.3).

**Обобщённая стоимость** (функция веса ребра для поиска пути):

```
G = w_cost · (топливо + сборы) + w_time · (время ТС и водителя) + w_risk · потери
```

Готовые наборы весов: «Баланс» (1, 1, 1), «Минимум затрат» (1.6, 0.6, 1), «Скорость доставки» (0.7, 2.2, 1), «Сохранность груза» (0.9, 0.8, 4).

### 5.3 Алгоритм Дейкстры с учётом времени

`Network.shortest()` — модифицированный алгоритм Дейкстры. Вместе с узлом хранится **часы с момента отправления**. Вес следующего ребра считается по прогнозу загруженности на тот час, когда машина до него доедет: `departure + clock`. Если выехать в 8:00, городской участок через 6 часов будет оценён по прогнозу на 14:00, а не на 8:00.

- Перекрытые участки (`перекрытие`, severity = 1) исключаются из графа.
- Режим `mode="distance"` ищет кратчайший путь по километрам без учёта обстановки. Это модель «традиционного» выбора маршрута, с которой сравнивается ИИ.
- Метод использует приближение FIFO (в общем случае задача с изменяющимися во времени весами сложнее). Поэтому `best_route()` дополнительно проверяет маршрут, кратчайший по километрам, и возвращает тот из двух вариантов, у которого обобщённая стоимость ниже.

### 5.4 k лучших маршрутов: алгоритм Йена

`Network.k_routes(k=3)` реализует алгоритм Йена:

1. Первый маршрут находится алгоритмом Дейкстры.
2. Для каждого узла-развилки (spur node) предыдущего маршрута:
   - корневая часть пути фиксируется;
   - запрещаются рёбра, по которым уже найденные маршруты с тем же корнем выходят из развилки, и узлы корня, чтобы не было циклов;
   - от развилки ищется путь с учётом времени, накопленного на корневой части.
3. Кандидаты помещаются в очередь с приоритетом по обобщённой стоимости. Дубликаты отсекаются по кортежу рёбер.
4. Если кратчайший по километрам путь не перекрыт и дешевле худшего найденного, он тоже добавляется в набор.

### 5.5 Полная оценка маршрута

`Network.evaluate()` последовательно проходит по рёбрам, сдвигает время и суммирует показатели. Здесь же учитывается **режим труда и отдыха водителя**:

- после каждых 4.5 ч за рулём — перерыв 45 мин;
- после каждых 9 ч за рулём — ежедневный отдых 10 ч 15 мин;
- простой ТС во время отдыха учитывается как 50 % ставки ТС.

Если маршрут проходит через перекрытие (возможно только у «традиционного» варианта), начисляется штраф: 10 ч простоя или объезда, и маршрут помечается флагом `closed`.

Результат (`RouteResult`) содержит км, время за рулём, отдых и погранпереходы, топливо в литрах и рублях, сборы, стоимость времени, потери, обобщённую стоимость, время прибытия и детализацию по участкам.

## 6. Диспетчеризация и загрузка ТС (`ai/dispatcher.py`)

Задача относится к классу VRP (Vehicle Routing Problem) с неоднородным парком, ограничениями по типу кузова и грузоподъёмности, сроками доставки и несколькими рейсами одной машины. Точное решение NP-трудно, поэтому используется конвейер эвристик.

### 6.1 Конвейер

```
Заказы (новые)
   │
   ▼ 1. Дробление        крупные заказы → части ≤ макс. грузоподъёмности кузова
   ▼ 2. Консолидация     First-Fit Decreasing по группам (пункт погрузки, кузов)
   │                     + мульти-дроп для тентов (до 2 точек выгрузки)
   ▼ 3. Матрицы подачи   дерево кратчайших путей порожняком от каждого узла (на тип кузова)
   ▼ 4. Назначение       жадный алгоритм с сожалением (regret insertion)
   ▼ 5. Локальный поиск  relocate / reorder между цепочками ТС
   ▼ 6. Сборка цепочек   точная оценка всех плеч с учётом времени
   ▼ 7. Базовая схема    расчёт «как обычно» для сравнения
   ▼ 8. Утверждение      запись рейсов, статусов, остатков заказов в БД
```

### 6.2 Консолидация и мульти-дроп

Внутри группы «пункт погрузки + тип кузова» части заказов сортируются по убыванию массы и раскладываются по загрузкам методом First-Fit Decreasing. Для тентов допускается вторая точка выгрузки, если выполнены оба условия:

```
dist(A, B) ≤ 450 км   и   min(dist(O,A), dist(O,B)) + dist(A,B) ≤ 1.25 · max(dist(O,A), dist(O,B)) + 60
```

Точки выгрузки идут в порядке удаления от пункта погрузки.

### 6.3 Назначение с сожалением

Для каждой неназначенной загрузки и каждого подходящего ТС (совпадает тип кузова, в цепочке меньше 4 загрузок, ТС укладывается в горизонт 96 ч) считается **предельная стоимость** её добавления в конец цепочки:

```
Δ = подача(loc → O) + маршрут(загрузки) + возврат(D_last → база) − возврат(loc → база)
    + штраф_опоздания · часы_опоздания + 1500 · (1 − коэфф. использования грузоподъёмности)
```

Если ТС меньше загрузки, `Δ` масштабируется на `weight / capacity` плюс 800 ₽ на дополнительный рейс. После назначения загрузка делится, остаток возвращается в очередь.

**Сожаление** — разница между лучшим и вторым лучшим вариантом. Она умножается на коэффициент приоритета: 1.6 для высокого, 1.0 для обычного, 0.7 для низкого. Первой назначается загрузка с наибольшим сожалением, то есть та, для которой промедление обойдётся дороже всего. Затем позиция и часы занятости ТС обновляются. Так естественно возникают **обратные загрузки**: машина, доставившая груз в Казань, получает ближайшую погрузку в Абсалямово, а не едет пустой.

### 6.4 Локальный поиск

До 6 проходов, на каждом для каждой загрузки:

- **relocate** — перенос в любую позицию цепочки другого подходящего ТС, включая ещё не задействованные;
- **reorder** — перестановка внутри своей цепочки.

Ход принимается, если суммарная стоимость цепочек снижается больше чем на 50 ₽. Стоимость цепочки считается по матрицам подачи. Выход за горизонт (96 + 48 ч) штрафуется по 2000 ₽/ч.

### 6.5 Базовая схема для сравнения

Каждый заказ перевозится отдельно машиной своей площадки (или ближайшей базы с нужным кузовом) по **кратчайшему по километрам** маршруту, с подачей и возвратом порожняком. Показатели считаются той же стоимостной моделью при той же дорожной обстановке. Поэтому разница показывает вклад ИИ: консолидации, обратных загрузок и учёта обстановки при выборе пути. На демо-данных снижение затрат составляет **9–14 %**, холостого пробега — **12–18 %**.

## 7. Интерфейс

- **Карта** (`MapCanvas`) — векторная отрисовка на `tk.Canvas` в равнопромежуточной проекции с поправкой `cos(52°)`. Есть зум колесом относительно курсора, панорамирование, тултипы участков с прогнозом ИИ, слои и легенда. Карта не требует подложки и интернета. Один и тот же виджет используется на вкладках «Обзор», «Карта», «Маршрут», «Рейсы» и в окне плана.
- **Графики** (`Chart`) — столбчатые (вертикальные и горизонтальные, в том числе с отрицательными значениями) и линейные диаграммы на Canvas с перерисовкой при изменении размера.
- **Таблицы** — `ttk.Treeview` с сортировкой по клику на заголовок (числа сортируются как числа) и цветовыми тегами статусов.

## 8. Развитие: путь к промышленной версии

### 8.1 Нейросетевая модель трафика

Когда накопится реальная телеметрия (сотни тысяч точек и больше), линейную модель стоит заменить нейросетью. Интерфейс `TrafficModel` (`train()`, `predict()`, `metrics`, `importance()`) уже изолирован, поэтому замена затронет один модуль.

| Этап | Технология | Описание |
|---|---|---|
| Базовая нелинейная модель | scikit-learn `GradientBoostingRegressor` / LightGBM | Те же признаки плюс `road_id` как категориальный признак; обычно даёт прирост на табличных данных |
| MLP | PyTorch / scikit-learn `MLPRegressor` | Эмбеддинги участков (8–16), циклическое кодирование часа (sin/cos), 2–3 скрытых слоя по 64 нейрона, ReLU, Dropout 0.1, Adam, loss MSE или Huber, ранняя остановка по валидации |
| Пространственно-временная модель | PyTorch Geometric (GCN + GRU / T-GCN) | Учитывает распространение заторов по соседним участкам графа и прогноз на несколько шагов вперёд |
| Экспорт и инференс | ONNX + `onnxruntime` | Обученная модель сохраняется в `model_meta`/файл, инференс без PyTorch в десктопном приложении |

Метрики и разбиение (80/20, затем кросс-валидация по времени — TimeSeriesSplit) остаются прежними, поэтому модели можно сравнивать напрямую на вкладке «Аналитика ИИ».

### 8.2 Источники данных

- **GPS/ГЛОНАСС-трекеры** парка: фактические скорости по участкам → `traffic_history`.
- **Яндекс.Карты / 2ГИС API**: дорожная обстановка, пробки, перекрытия → `road_events`.
- **Погодные API** (Яндекс.Погода, OpenWeatherMap) → `weather`.
- **1С / ERP**: заказы, остатки на площадках, справочник автопарка → `orders`, `nodes`, `vehicles`.
- **Детальный граф дорог** (OpenStreetMap + OSRM / Valhalla) вместо агрегированного графа «город — город».

### 8.3 Оптимизация

- Замена эвристик диспетчеризации на **Google OR-Tools** (CVRPTW с неоднородным парком, pickup & delivery) или на метаэвристики ALNS / Tabu Search для крупных задач.
- Мультимодальность: железнодорожные перевозки гипсового камня и цемента с узлами перевалки.
- Стохастическая оптимизация: доверительные интервалы прогноза загруженности в стоимости маршрута (робастный выбор).

### 8.4 Платформа

- Серверная БД (PostgreSQL + PostGIS), REST API (FastAPI), многопользовательский режим и роли (логист, диспетчер, руководитель).
- Мобильное приложение водителя: задание на рейс, статусы, фотофиксация повреждений груза.
- Сборка дистрибутива для Windows: `pyinstaller --noconsole --name VolmaLogistics main.py`. Путь к БД уже учитывает режим `sys.frozen`.

## 9. Ограничения MVP

- Граф дорог агрегирован до уровня «город — город». Расстояния приблизительные: гаверсинус × коэффициент извилистости.
- История трафика, телеметрия, дорожные события («Получить обновление обстановки») и координаты месторождений — демонстрационные данные.
- Алгоритм Дейкстры с изменяющимися во времени весами использует приближение FIFO. Ожидание в узле ради объезда пика не моделируется.
- Если заказ разделён на несколько рейсов, в нём хранится ссылка только на первый рейс.
- Экономия по отдельному рейсу может быть отрицательной: например, когда ТС подаётся издалека или начинает цепочку не со своей базы. Оптимизируется суммарная стоимость плана.
- Однопользовательский режим: БД — локальный файл без разграничения доступа.

## 10. Проверка и отладка

- **Быстрая проверка логики без GUI**:

  ```python
  from volma.db import Database
  from volma.ai.traffic_model import TrafficModel
  from volma.ai.network import Network, next_departure
  from volma.ai.dispatcher import Dispatcher

  db = Database("test.db")
  model = TrafficModel(db)
  net = Network(db, model)
  ids = {r["code"]: r["id"] for r in db.q("SELECT id, code FROM nodes")}
  routes = net.k_routes(ids["IND"], ids["SRT"], next_departure(8), net.profile_for(None, "тент"), "DRY_MIX", 20)
  plan = Dispatcher(db, net).plan()
  print(model.metrics, plan["optimized"], plan["baseline_served"])
  ```

- **Сброс данных**: «Справочники» → «Сбросить демо-данные» или удаление файла `data/volma.db`.
- **Детерминизм**: демо-данные генерируются с фиксированным зерном (`random.Random(2026)`), поэтому результаты воспроизводимы. Исключения — кнопка «Получить обновление обстановки» и телеметрия закрытых рейсов.
- **Соглашение по коду**: в исходных файлах нет комментариев (требование проекта). Вся пояснительная документация находится в `README.md` и `DEVREADME.md`.
